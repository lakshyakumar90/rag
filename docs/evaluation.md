# RAG evaluation results

Generated by `evals/evaluate.py`; raw numbers are in `evals/results.json`.
Rerun after any change to chunking, retrieval, prompting or reranking:

```bash
.venv/Scripts/python.exe evals/evaluate.py
```

## Dataset

- **Corpus:** 5 internal-handbook documents (onboarding, benefits, expenses,
  security, troubleshooting), 15 explicitly numbered pages.
- **Questions:** 42 — 36 answerable with an expected answer string, expected
  document and expected page, plus 6 deliberately unanswerable questions.
- **Ground truth:** `evals/questions.jsonl`; page markers are embedded in the
  corpus files.

## Metrics

| Metric | Definition |
|---|---|
| `hit@k` | Answerable questions with an expected-document **and** expected-page chunk in the top k. |
| `answer_correctness` | Answerable answers containing the normalized expected answer. |
| `citation_accuracy` | Answerable questions with a citation to the expected document and page. |
| `idk_accuracy` | Unanswerable questions answered exactly "I don't know". |
| `false_idk_rate` | Answerable questions answered "I don't know". |

The harness uses the real chunker, retrieval repository, RRF fusion, rerank
hook, prompt builder, `ChatService.answer` and citation parser. Embeddings,
reranking and answer generation are deterministic local stand-ins (documented
in `evals/README.md`), so treat the numbers as *relative* comparisons, not as
production quality scores.

## Configuration

Production defaults held constant across runs: `candidate_k=20`, `top_k=5`,
`score_threshold=0.15`, `rrf_k=60`, prompt budget 2000 tokens. The matrix varies
chunk size (128/256/512 tokens, 20% overlap), embedder (hashing-256,
hashing-768, tfidf-768), retrieval mode (vector-only, hybrid) and reranking
(off/on) — 36 configurations × 42 questions.

Results are from SQLite, where vector search is Python cosine similarity and
keyword search is substring matching. On Postgres the same code uses pgvector
and `tsvector`/`ts_rank_cd`, so absolute numbers may differ.

## Which retrieval settings work best

| Setting | Measured best | Recommendation |
|---|---|---|
| Chunk size | 256–512 tokens (hit@1 0.815) | **256 tokens, 20% overlap** — 512 ties on quality but costs more storage |
| Embedding | tfidf-768 (hit@1 0.884, answer 0.833) | **best available embedding model**; avoid small hashed vectors |
| Retrieval mode | vector and hybrid tie at 0.812 on SQLite | **hybrid** — Postgres `tsvector` adds stemming; re-measure there |
| Reranking | on (hit@1 0.877 vs 0.747 off) | **enabled** |
| Candidate / final k | 20 / 5 | keep `candidate_k=20`, `top_k=5` |

Best single configuration: `chunk=128 tfidf-768 vector rerank` (hit@1 0.944,
answer 0.833, citation 0.944). The 256-token equivalent is effectively tied and
is the safer default for longer documents.

## Findings

1. **Reranking is the largest single win.** Averaged hit@1 rises from 0.747 to
   0.877 (+0.13) and hit@5 reaches 1.000. Even a cheap lexical reranker
   outperforms RRF ordering alone; a real cross-encoder should be benchmarked
   next.
2. **Embedding quality dominates the weak configurations.** Corpus-fitted TF-IDF
   beats signed feature hashing by ~0.13 hit@1 and ~0.055 answer correctness.
   Small hashed vectors collide badly on short documents; with a real embedding
   model, this comparison should be rerun rather than assumed.
3. **Chunk size matters only with weak retrieval.** 256 and 512 tokens are
   virtually tied (0.815 hit@1) and slightly better than 128 (0.806). The gap
   widens to 0.23 hit@1 for hashing-256, where aggressive chunking fragments
   evidence. Prefer 256–512 tokens for this document profile.
4. **Hybrid and vector-only are indistinguishable here** (identical averages,
   tiny differences at hit@3). The SQLite keyword fallback is plain substring
   matching; Postgres full-text search with stemming should be measured before
   concluding that the keyword leg adds nothing.
5. **The current abstention logic never fires.** `idk_accuracy = 0.000` and
   `false_idk_rate = 0.000` across all 36 runs: every question, including the
   six unanswerable ones, produced a confident answer. The cause is structural,
   not tuning: RRF normalizes rank 1 to exactly 1.0 and rank 5 to ~0.94 with
   `k=60`, so `score_threshold=0.15` is always satisfied whenever retrieval
   returns any chunk. Applying the threshold to pre-fusion scores, or adding a
   calibrated evidence check, is required before "I don't know" is meaningful.
6. **Citation accuracy tracks answer correctness** (0.847–0.926 across
   embedders). The residual errors are cases where two documents contain
   similar numbers (for example "30 days" or "14 days") and the wrong source
   was cited — exactly the case a stronger reranker should help with.

## Recommended next steps

- Apply the relevance threshold before RRF fusion and re-run to get a
  meaningful "I don't know" baseline.
- Evaluate a real embedding model and a cross-encoder reranker (the harness
  accepts any object exposing `embed_query`/`embed_documents` and `rerank`).
- Re-run against Postgres to measure `tsvector` boosting in hybrid mode.
- Replace `ExtractiveLLM` with the configured LLM to measure answer quality and
  hallucination rather than evidence selection alone.
